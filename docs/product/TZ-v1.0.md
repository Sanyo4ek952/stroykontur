# Техническое задание
## Строительное PWA для управления объектом строительства

**Файл:** `docs/product/TZ-v1.0.md`  
**Версия:** 1.0  
**Статус:** базовая версия после логического аудита  
**Основание:** анализ предоставленных архивов строительной документации и согласованные требования к ролям, ответственности и цифровым процессам.

> Подробные правила ролей, workflows, доменной модели и архитектуры вынесены в отдельные документы и имеют более высокий приоритет согласно `AGENTS.md`.

---

# 1. Назначение системы

Разработать mobile-first PWA для управления строительным объектом, объединяющее:

- проектную и рабочую документацию;
- производство строительно-монтажных работ;
- планирование и фактическое выполнение;
- участников проекта и зоны ответственности;
- материалы и ТМЦ;
- охрану труда и наряды-допуски;
- геодезию;
- строительный контроль и качество;
- исполнительную документацию;
- электронные производственные журналы;
- КС, договоры, сметы и оплату;
- замечания, технические запросы и согласования;
- уведомления и историю изменений.

По любой работе система должна отвечать:

1. Что сейчас происходит?
2. Кто отвечает?
3. Что уже выполнено?
4. Что мешает продолжению?
5. Какие документы и условия необходимы?
6. Что изменилось?
7. Кто должен действовать следующим?

PWA не должно быть цифровой копией папок Windows. Центральная сущность — **строительная работа (Work / Work Item)**.

---

# 2. Цели проекта

1. Дать каждому участнику актуальную информацию в пределах его зоны ответственности.
2. Исключить работу по устаревшей проектной документации.
3. Показывать фактическую готовность каждой работы к следующему этапу.
4. Связывать изменения документов и работ с затрагиваемыми участниками.
5. Снизить количество ручных звонков, переписок и дублирования информации.
6. Сделать прозрачными причины простоев и отклонений.
7. Обеспечить прослеживаемость: проект → работа → материал → люди → качество → ИД → КС → оплата.
8. Перевести производственные журналы в структурированный электронный вид.
9. Сохранять полную историю действий и изменений.
10. Обеспечить удобную мобильную работу на строительной площадке.

---

# 3. Общая модель строительного проекта

```text
Проект / строительный комплекс
└── Объект
    └── Позиция по генеральному плану
        └── Зона / захватка
            └── Конструктивный элемент
                └── Вид работы
                    └── Work Item
```

Один комплект рабочей документации может относиться к одной или нескольким зонам. Связи документов, зон и работ должны поддерживать many-to-many там, где это необходимо.

---

# 4. Организации и участники проекта

Система должна учитывать:

- Organization;
- участие организации в проекте;
- сотрудников организации;
- организацию-исполнителя Work;
- внешних участников.

Типы организаций: заказчик, генподрядчик, подрядчик, субподрядчик, проектировщик, лаборатория, поставщик и др.

---

# 5. Основные роли

- Акционер;
- Директор;
- Директор по строительству;
- Начальник участка;
- ПТО;
- Геодезия;
- Делопроизводитель;
- Мастер;
- Инженер по охране труда;
- Снабженец;
- Инженер строительного контроля от генподрядчика.

Архитектура должна позволять добавлять финансы/бухгалтерию, кладовщика, лабораторию, техзаказчика, авторский надзор, проектировщика и других внешних участников.

---

# 6. Зафиксированные владельцы процессов

- Инженер по охране труда — ОТ/ТБ, допуски, удостоверения, высотные и огневые работы, наряды-допуски.
- Снабженец — снабжение и ТМЦ.
- Инженер строительного контроля от генподрядчика — строительный контроль и качество.
- ПТО — техническая и исполнительная документация в пределах утверждённых workflow.
- Директор по строительству / начальник участка — производственный контур.
- Мастер — первичная фиксация выполнения на площадке.

---

# 7. Модель доступа

Не использовать жёсткую модель `if role == ...`.

Доступ строится как:

```text
Resource + Action + Scope
```

Нужно поддерживать чтение, создание, редактирование, согласование, возврат, утверждение, выдачу в производство, закрытие, просмотр истории и ограничения по проекту/зоне/организации/процессу.

---

# 8. Центральная сущность — Work

Work описывает конкретную строительную работу и связывается с:

- ProjectArea;
- видом работы;
- организацией-исполнителем;
- ответственными;
- сроками;
- объёмами;
- РД;
- материалами;
- людьми;
- ОТ/ТБ;
- геодезией;
- качеством;
- ИД;
- КС;
- деньгами;
- событиями;
- аудитом.

---

# 9. Раздельные показатели объёма

Хранить отдельно:

1. `Produced` — производственно выполнено.
2. `Accepted` — принято контролем.
3. `ID Ready` — обеспечено комплектной ИД.
4. `KS Closed` — включено в КС.

Один показатель не должен автоматически подменять другой.

---

# 10. Жизненный цикл Work

```text
Создана
→ Подготовка
→ Готова
→ В работе
→ Производственно завершена
→ Контроль
→ Принята
→ ИД комплектна
→ Доступна к КС
→ Закрыта
```

Конкретные переходы определяются workflow и контрольными точками.

---

# 11. QualityGate / ControlPoint

Контрольная точка может требоваться до начала, во время или после выполнения.

Примеры:

- геодезическая разбивка;
- приёмка армирования;
- проверка опалубки;
- отбор проб;
- исполнительная съёмка;
- освидетельствование скрытых работ.

Обязательная контрольная точка блокирует соответствующий переход Work до прохождения.

---

# 12. Work Readiness

Готовность определяется через ReadinessRule.

Категории требований:

- актуальная РД;
- ППР;
- предыдущая работа;
- материал;
- документы качества;
- люди и квалификация;
- наряд-допуск;
- геодезия;
- строительный контроль;
- лаборатория;
- техника;
- внешнее согласование.

Невыполненное обязательное условие создаёт WorkBlocker.

---

# 13. Планирование

Для Work учитывать плановый старт/финиш, длительность, зависимости, плановый объём, факт, прогноз окончания, отклонение и критичность.

---

# 14. Сменные задания

DailyAssignment включает дату, зону, Work, мастера, бригаду, плановый объём, материалы, технику, комментарий и статус.

После смены фиксируются план, факт, отклонение и причина.

---

# 15. Ежедневные отчёты

Структурированные данные:

- дата;
- зона;
- Work;
- ИТР;
- рабочие;
- фактический объём;
- время;
- техника;
- фото;
- простой;
- причина;
- комментарий.

Подтверждённый факт не должен незаметно переписываться.

---

# 16. Рабочая документация

Структура:

```text
DesignDiscipline
→ TechnicalDocument / Package
→ DocumentRevision
→ Review
→ IssueForWork
```

Предыдущие ревизии сохраняются. Аннулированные документы остаются в истории.

---

# 17. Изменения РД

DocumentImpact должен фиксировать новую ревизию, затронутые Work, зоны, ответственных и необходимые действия.

Изменение активной Work является событием повышенного приоритета.

---

# 18. Выдача РД в производство

Фиксировать кто, когда, какую ревизию, для какой области и каких Work выдал в производство, а также подтверждение ознакомления при необходимости.

---

# 19. Технические запросы / RFI

RFI связывается с Work и документацией. Ответ RFI не становится автоматически новой действующей РД, если меняется проектное решение.

Правильная цепочка:

```text
RFI
→ DesignChange
→ новая Revision
→ IssueForWork
```

---

# 20. Документооборот

Поддержать входящую, исходящую и внутреннюю корреспонденцию с регистрацией, адресатами, сроками, подтверждением получения и вложениями.

---

# 21. Замечания

Issue имеет описание, Work/зону, фото, автора, ответственного, критичность, срок, действия и повторную проверку.

```text
OPEN
→ IN_PROGRESS
→ READY_FOR_REINSPECTION
→ VERIFIED
→ CLOSED
```

Исполнитель не закрывает замечание окончательно без требуемой проверки.

---

# 22. Строительный контроль / качество

Владелец — инженер строительного контроля от генподрядчика.

Функции: проверки, чек-листы, замечания, повторная проверка, подтверждение качества, контроль соответствия РД, участие в ИД и входном контроле материалов.

---

# 23. Геодезия

Поддержать GeodeticTask, GeodeticSurvey, GeodeticScheme, GeodeticInstrument, поверки, отклонения и повторные съёмки.

Геодезия может быть обязательной контрольной точкой.

---

# 24. ОТ/ТБ и наряды-допуски

Для Employee учитывать квалификацию, удостоверения, инструктажи, специальные допуски и сроки действия.

WorkPermit должен поддерживать высотные и огневые работы, состав бригады, ответственных, меры безопасности, СИЗ, период, открытие, приостановку, продление и закрытие.

Work не должна начинаться без обязательного действующего допуска.

---

# 27. Строительная техника и оборудование

Предусмотреть Equipment и EquipmentAssignment с учётом владельца, доступности, проверок и назначения на Work/смену.

---

# 28. Лабораторный контроль

Поддержать LabSample, LabTest и LabProtocol с привязкой к MaterialBatch и Work.

---

# 30. Электронные производственные журналы

Журналы должны быть структурированными электронными сущностями, а не просто Excel/PDF.

Общее:

- ElectronicJournal;
- JournalEntry;
- JournalEntryRevision;
- регистрационный номер;
- автор;
- дата;
- Work;
- вложения;
- статус;
- история.

Подтверждённая запись исправляется корректирующей записью/ревизией.

Предусмотреть минимум общий журнал работ, сварочные, бетонные, уход за бетоном, входной контроль, монтаж конструкций, высокопрочные болты, подготовку поверхности и геодезические журналы.

# 35. Согласования

Approval используется как общий механизм решений для документов, заявок, дополнительных работ, КС, оплат и других процессов.

---

# 36. Внешние участники

Поддержать ограниченный доступ для технического заказчика, авторского надзора, проектировщика и других внешних участников.

---

# 37. Уведомления и события

Уведомления создаются по бизнес-событиям, а не по каждому сохранению файла.

Примеры: DOCUMENT_REVISION_CREATED, WORK_BLOCKED, QUALITY_ISSUE_CREATED, MATERIAL_DELIVERED, SAFETY_ADMISSION_EXPIRED, ID_COMPLETE, KS_READY, PAYMENT_COMPLETED.

Критичные события могут требовать acknowledgement, Task и эскалацию.

---

# 38. Задачи

Task должен иметь исполнителя, инициатора, Project, связанный бизнес-объект, срок, приоритет, статус и основание.

---

# 39. История и аудит

Для значимых действий фиксировать actor, контекст роли, Project, сущность, действие, before/after, дату/время и причину.

Критичные данные не удаляются без следа.

# 47. Ключевые бизнес-правила

1. Нельзя заменить утверждённую ревизию без сохранения предыдущей.
2. Аннулированная РД остаётся в истории.
3. Активная Work связана с конкретной применимой ревизией.
4. Изменение РД запускает анализ затронутых Work.
5. Work нельзя начать при невыполненной обязательной готовности.
6. Work нельзя начать без обязательного действующего WorkPermit.
7. Employee не назначается на специальную работу без действующего допуска.
8. Material должен быть прослеживаем до Work, когда это требуется.
9. Исполнитель не закрывает замечание окончательно без требуемой проверки.
10. Объём КС сверяется с production-фактом и принятым объёмом.
11. Электронные журналы сохраняют историю.
12. Согласования хранят автора, дату и решение.
13. Override логируется с причиной.
14. Пользователь видит только разрешённые Project/Organization/Areas.
15. `Produced`, `Accepted`, `ID Ready`, `KS Closed` — разные показатели.
16. Ответ RFI не изменяет действующую РД без DesignChange/новой ревизии.
17. Обязательный ControlPoint должен быть пройден до соответствующего перехода.
18. Подтверждённая JournalEntry исправляется только корректирующей записью/ревизией.
19. Замена материала, влияющая на проект/качество, требует согласования.
20. Для каждой активной блокировки должен существовать владелец следующего действия.

# 48. Основные сквозные процессы

## Проектирование → строительство

```text
РД → Revision → Review → Approval → IssueForWork → Work
```

## Производство

```text
План → DailyAssignment → Readiness → Work ↕ ControlPoints → WorkProgress
```

## Качество

```text
Work → Inspection → Issue → исправление → reinspection → Accepted
```

## Геодезия

```text
ControlPoint → GeodeticTask → Survey → Result
```

## Материалы

```text
Requirement → Request → Purchase → Delivery → IncomingInspection → MaterialBatch → Work
```

## ОТ/ТБ

```text
Employee → Certificates → Admission → WorkPermit → Briefing → разрешение
```

## ИД → КС → деньги

# 50. Что система не должна делать

- превращаться в файловый менеджер;
- позволять работать по неизвестной ревизии;
- скрывать старые версии;
- уведомлять на каждое сохранение;
- давать всем ролям одинаковый интерфейс;
- позволять исполнителю окончательно принимать собственную работу;
- хранить КС независимо от production-факта;
- считать наличие PDF достаточным подтверждением процесса;
- удалять историю критичных изменений.

# 51. Критерии успешности

По любой активной Work должно быть возможно определить:

1. что это за работа;
2. где выполняется;
3. кто отвечает;
4. по какой РД выполняется;
5. какая ревизия актуальна;
6. можно ли продолжать;
7. если нет — почему;
8. кто назначен;
9. есть ли допуски;
10. есть ли материал;
11. что произведено фактически;
12. есть ли замечания;
13. какие ControlPoints пройдены;
14. принято ли качество;
15. готова ли ИД;
16. включён ли объём в КС;
17. оплачено ли основание;
18. какие изменения происходили;
19. какие контрольные точки обязательны;
20. сколько Produced / Accepted / ID Ready / KS Closed;
21. какая организация выполняет работу.

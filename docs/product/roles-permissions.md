# PWA строительного объекта — роли и права доступа

**Файл:** `docs/product/roles-permissions.md`  
**Версия:** 0.2  
**Основание:** ТЗ 1.0 + `modules.md`  
**Статус:** бизнес-модель доступа до проектирования БД/API/UI

---

# 1. Цель документа

Документ определяет:

- какие роли существуют в проекте;
- за какие процессы отвечает каждая роль;
- кто может видеть, создавать, изменять, согласовывать и закрывать данные;
- кто получает уведомления;
- какие действия должны быть запрещены независимо от UI;
- какие права зависят от статуса бизнес-процесса.

Этот документ не определяет техническую реализацию авторизации.

---

# 2. Основные принципы

## 2.1. Доступ определяется не страницей, а действием

Недостаточно правила:

> «ПТО имеет доступ к разделу ИД».

Нужно различать:

- просмотр;
- создание;
- редактирование черновика;
- отправка на согласование;
- согласование;
- возврат на доработку;
- закрытие;
- отмена;
- просмотр истории;
- работа с вложениями.

---

## 2.2. Роль назначается в рамках объекта

Один пользователь может иметь разные роли на разных строительных объектах.

Пример:

- на объекте A — начальник участка;
- на объекте B — наблюдатель или другая роль.

Права не должны назначаться только глобально на пользователя.

### Организационный контекст

Project может включать несколько Organization. ProjectMember действует от имени конкретной ProjectOrganization. По умолчанию пользователь не получает доступ к данным другой организации только потому, что имеет такую же Role на том же Project. Межорганизационный доступ должен следовать из permission/scope или явного workflow.

---

## 2.3. Владелец процесса — не обязательно единственный исполнитель

Владелец процесса отвечает за его корректность и итоговое состояние.

Пример:

- мастер может создать заявку на материал;
- снабженец является владельцем процесса снабжения;
- директор по строительству может согласовать критическую заявку.

---

## 2.4. Закрытые и согласованные данные нельзя тихо переписывать

После согласования, подписания или закрытия:

- запрещено незаметно изменять исходную запись;
- изменение должно выполняться через новую версию, корректировку, отмену или повторное открытие;
- причина изменения обязательна;
- событие фиксируется в Audit.

---

## 2.5. Удаление бизнес-данных должно быть исключением

Для большинства рабочих сущностей:

- работы;
- документов;
- заявок;
- замечаний;
- ИД;
- КС;
- платежей;
- записей журналов

предпочтительны:

- отмена;
- архивирование;
- аннулирование;
- новая версия.

Hard delete не является обычным пользовательским действием.

---

## 2.6. Руководящая роль не должна разрушать ответственность процесса

Высокий уровень доступа не означает, что директор должен вручную выполнять действия ПТО, снабженца или инженера ОТ в обычном процессе.

Рекомендуется:

- директор видит всё;
- может выполнять административный override;
- override требует причины;
- действие явно фиксируется в истории.

Это лучше, чем единое правило «директор может всё без ограничений».

# 3. Системные типы полномочий

Используем следующие обозначения.

| Код | Полномочие |
|---|---|
| V | View — просмотр |
| C | Create — создание |
| E | Edit — изменение черновика/рабочей записи |
| S | Submit — отправка на согласование/проверку |
| A | Approve — согласование/принятие |
| R | Return — возврат на доработку |
| CL | Close — закрытие процесса |
| AS | Assign — назначение ответственного |
| M | Manage — управление процессом |
| O | Override — административное вмешательство |
| H | History — просмотр истории/Audit |

Права всегда дополнительно ограничиваются Project, ProjectOrganization, ProjectArea/зоной ответственности и статусом сущности.

# 4. Основные роли проекта

## R01. Акционер

### Назначение

Наблюдение за состоянием проекта без операционного вмешательства.

### Основные права

- просмотр состояния объекта;
- просмотр прогресса;
- просмотр документов;
- просмотр снабжения;
- просмотр качества;
- просмотр ИД;
- просмотр КС и финансовых показателей при соответствующей политике;
- просмотр истории.

### Ограничения

- не создаёт операционные записи;
- не редактирует;
- не согласовывает;
- не закрывает процессы.

**Базовый профиль:** read-only.

---

# R02. Директор

### Назначение

Управленческий контроль проекта и принятие решений верхнего уровня.

### Основные права

- полный обзор объекта;
- просмотр всех бизнес-процессов;
- назначение ключевых ответственных;
- согласование процессов, где директор указан согласующим;
- административный override с обязательной причиной;
- просмотр Audit.

### Рекомендация

Не использовать директора как штатного исполнителя всех процессов.

---

# R03. Директор по строительству

### Назначение

Владелец производственного контура строительства.

### Зона ответственности

- ход работ;
- планирование;
- приоритеты;
- ответственные;
- производственные блокировки;
- связь работ с проектной документацией;
- координация участка, ПТО, снабжения и контроля.

### Основные права

- управление производственными работами;
- назначение ответственных;
- согласование производственных решений;
- контроль изменений проектной документации;
- просмотр снабжения, качества, ИД и КС;
- эскалация проблем.

---

# R04. Начальник участка

### Назначение

Оперативное управление строительным участком.

### Зона ответственности

- работы на участке;
- мастера;
- фактическое выполнение;
- потребность в материалах;
- готовность работ к контролю;
- устранение производственных замечаний.

### Основные права

- создание/изменение производственных работ в своей зоне;
- подтверждение фактического выполнения;
- назначение мастеров;
- создание и согласование заявок в пределах процесса;
- отправка работ на контроль;
- реакция на изменения документации;
- закрытие оперативных задач.

---

# R05. ПТО

### Назначение

Владелец технической документации и исполнительной документации в пределах своей компетенции.

### Зона ответственности

- проектная/рабочая документация;
- ревизии;
- выдача документов в производственный процесс по установленному workflow;
- исполнительная документация;
- реестры ИД;
- АОСР;
- исполнительные схемы;
- подготовка данных для закрытия объёмов.

### Основные права

- регистрация и ведение технической документации;
- создание новых ревизий;
- формирование комплектов ИД;
- отправка ИД на проверку;
- возврат технических материалов на доработку;
- просмотр выполнения и качества.

---

# R06. Делопроизводитель

### Назначение

Административное сопровождение документов.

### Зона ответственности

- регистрация документов;
- загрузка файлов;
- реквизиты;
- входящая/исходящая документация;
- договорные и административные вложения;
- контроль комплектности файлов.

### Ограничение

Делопроизводитель управляет документом как административной единицей, но не должен единолично менять технический смысл проектной документации или принимать выполненные работы.

---

# R07. Мастер

### Назначение

Первичный источник фактической информации с площадки.

### Зона ответственности

- ежедневные работы;
- состав бригады;
- фактические объёмы;
- потребность в материалах;
- фиксация проблем;
- готовность этапа к следующему действию.

### Основные права

- заполнение ежедневного отчёта;
- обновление факта выполнения назначенных работ;
- создание заявки на материалы;
- создание производственной проблемы;
- просмотр актуальной рабочей документации;
- подтверждение ознакомления с изменениями.

---

# R08. Инженер по охране труда

### Назначение

Владелец процессов ОТ/ТБ.

### Зона ответственности

- инструктажи;
- удостоверения;
- допуски;
- высотные работы;
- огневые работы;
- наряды-допуски;
- контроль сроков документов;
- ограничения допуска работников.

### Основные права

- управление ОТ/ТБ;
- выдача/регистрация допусков в пределах процесса;
- создание и сопровождение нарядов-допусков;
- блокирование допуска к работам при отсутствии обязательных требований;
- уведомление ответственных о нарушениях и истекающих документах.

---

# R09. Снабженец

### Назначение

Владелец процессов снабжения и ТМЦ.

### Зона ответственности

- обработка заявок;
- закупка/поставка;
- статусы поставки;
- приём движения ТМЦ в учётном процессе;
- связь материала с потребностью и работой.

### Основные права

- принятие заявки в работу;
- изменение статуса снабжения;
- регистрация поставки;
- управление позициями ТМЦ в рамках снабжения;
- фиксация отклонений поставки;
- уведомление производства об изменениях сроков.

---

# R10. Инженер строительного контроля от генподрядчика

### Назначение

Отдельная роль и владелец процесса строительного контроля качества.

### Зона ответственности

- проверки;
- контрольные точки;
- замечания;
- повторные проверки;
- подтверждение качества работ;
- входной контроль в пределах принятого процесса.

### Основные права

- принять вызов на контроль;
- провести проверку;
- создать замечание;
- вернуть работу на устранение;
- подтвердить устранение;
- принять работу по качеству;
- фиксировать результаты проверки.

---

# R11. Инженер-геодезист / Геодезия

### Назначение

Владелец геодезического сопровождения работ.

### Зона ответственности

- геодезические задания;
- разбивка и исполнительная съёмка;
- проектные/фактические значения;
- геодезические схемы;
- контроль приборов/поверок;
- фиксация отклонений;
- прохождение геодезических контрольных точек.

### Основные права

- создавать/принимать геодезические задания;
- регистрировать GeodeticSurvey;
- прикладывать GeodeticScheme;
- фиксировать отклонения;
- требовать исправление/повторную съёмку;
- подтверждать допустимый результат в пределах полномочий.

---

# 5. Роли, которые пока не фиксируем как окончательные

Для следующих контуров может потребоваться отдельная роль, но она не должна вводиться без подтверждённого бизнес-процесса:

- бухгалтер / финансист;
- сметчик;
- кадровик;
- администратор системы;
- представитель заказчика;
- внешний технический надзор;
- представитель субподрядчика;
- кладовщик.

До уточнения их действия либо остаются за существующими владельцами процессов, либо помечаются `TBD`.

# 6. Уровни области доступа

Одного набора CRUD-прав недостаточно.

Каждое право должно иметь scope.

## S01. SYSTEM

Доступ ко всей системе.

Используется только для технического администратора.

## S02. ORGANIZATION

Доступ ко всем объектам организации.

## S03. PROJECT

Доступ ко всему конкретному строительному объекту.

## S04. AREA

Доступ к назначенной захватке/зоне.

## S05. OWN_PROCESS

Доступ к процессам, владельцем или ответственным за которые является пользователь.

## S06. OWN_RECORD

Доступ только к собственным черновикам/записям.

# 7. Матрица верхнего уровня по модулям

Обозначения:

- `V` — просмотр;
- `M` — управление своим процессом;

- `—` — нет штатного полномочия.

| Проектная документация | V | V/O | A/V | V | M | M* | V | V | V | V |
| Производство | V | V/O | M/A | M | V | V | M | V | V | V |

| Контроль качества | V | V/O | V | C/R | V | V | C | V | V | M/A |
| ИД/ИТД | V | V/O | V/A | V | M | M* | C/V | V | V | A/V |
| Договоры | V | M/O | V | V | V | M | — | — | V | — |
| Сметы/допработы | V | A/O | A/V | C/V | M/V | V | C/V | — | V | V |

## 7.1. Дополнение v1.1 — Organization, геодезия и журналы

| Контур | Основной владелец | Базовое правило доступа |
|---|---|---|
| Organization / ProjectOrganization | директор / уполномоченная admin-функция | изменение состава организаций требует `project.organizations.manage`; видимость учитывает organization scope |
| Геодезия | инженер-геодезист | производство создаёт потребность/вызов, геодезист фиксирует и подтверждает результат |
| Электронные журналы | определяется JournalTypeDefinition | author/confirm/signoff права задаются типом журнала, а не единым глобальным владельцем |

Для журналов запрещена модель «одна роль редактирует все журналы». Общая платформа переиспользуется, но владелец и подписанты зависят от типа журнала.

# BP-15. События, уведомления и задачи

## Событие

Создаётся системой при значимом изменении.

Пользователь не должен вручную создавать техническое событие.

## Уведомление

Получатели определяются:

1. типом события;
2. объектом;
3. зоной ответственности;
4. связанной работой;
5. ролью;
6. назначенным ответственным.

## Задача

Может создаваться:

- автоматически правилом workflow;
- ответственным руководителем;
- владельцем процесса.

|---|---|

| Назначить | владелец процесса |
| Принять в работу | исполнитель |
| Изменять результат | исполнитель |
| Закрыть | исполнитель либо владелец по типу задачи |

| Удалить историю | запрещено |

# 9. Правила доступа по статусу

Права должны меняться вместе со статусом сущности.

Пример общей модели:

## Draft

Автор/владелец может:

- редактировать;
- добавлять вложения;
- отменять черновик.

## Submitted

Автор:

- больше не изменяет содержимое свободно;
- может отозвать только если workflow разрешает.

Согласующий:

- согласовать;
- вернуть;
- отклонить.

## Approved

Прямое редактирование запрещено.

Разрешены:

- новая версия;
- корректировка;
- аннулирование по установленному процессу.

## Closed

Изменение бизнес-содержимого запрещено.

Допустимы:

- комментарий;
- новый связанный процесс;
- специальная корректировка;
- административный override с причиной.

---

# 10. Наследование видимости

Пользователь видит сущность, если одновременно выполнены условия:

1. у него есть доступ к строительному объекту;
2. роль разрешает этот тип данных;
3. scope включает соответствующую захватку/зону либо процесс;
4. нет дополнительного ограничения на чувствительные данные.

Пример:

Мастер объекта A не должен автоматически видеть данные объекта B.

Мастер 3-й захватки может не иметь права изменять факт работ 7-й захватки.

---

# 11. Чувствительные данные

Отдельная политика доступа потребуется минимум для:

- паспортных данных;
- телефонов;
- кадровых документов;
- медицинских документов;
- зарплатных данных;
- банковских реквизитов;
- финансов;
- коммерческих условий договоров.

Наличие доступа к модулю не означает доступ ко всем полям сущности.

---

# 12. Audit обязателен для критических действий

Минимально фиксировать:

- пользователя;
- роль на момент действия;
- объект;
- сущность;
- действие;
- предыдущее состояние;
- новое состояние;
- дату/время;
- причину override/корректировки;
- связанную задачу или workflow при наличии.

Особенно обязательно для:

- ревизий проектной документации;
- согласований;
- качества;
- ОТ/ТБ;
- ИД;
- КС;
- оплат;
- изменения ролей и полномочий.

---

# 13. Что нельзя кодировать как hardcoded role checks

Нежелательная модель:

```text
if user.role == "director"
```

Бизнес-правило должно опираться на полномочие.

Пример:

```text
project.document.approve
work.daily_report.confirm
supply.request.manage
quality.inspection.accept
safety.work_permit.issue
```

Роль должна быть набором таких полномочий.

Это позволит позже изменить ответственность без переписывания десятков компонентов.

# 17. Граница этапа

После утверждения этого документа можно переходить к:

`docs/product/workflows.md`

На следующем этапе каждый BP-процесс раскладывается в state machine:

```text
Draft
→ Submitted
→ Review
→ Approved / Returned / Rejected
→ In Progress
→ Closed
```

Но статусы должны проектироваться отдельно для каждого реального процесса, а не создаваться одним универсальным шаблоном для всей системы.

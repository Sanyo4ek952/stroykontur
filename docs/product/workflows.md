# PWA строительного объекта — бизнес-процессы и workflows

**Файл:** `docs/product/workflows.md`  
**Версия:** 0.2  
**Основание:** ТЗ 1.0 + `modules.md` + `roles-permissions.md`  
**Статус:** предметная модель процессов до проектирования БД/API/UI

---

# 1. Цель документа

Документ фиксирует жизненный цикл основных процессов строительного объекта.

Для каждого процесса определяются:

- состояния;
- допустимые переходы;
- инициатор перехода;
- согласующий/проверяющий;
- условия перехода;
- создаваемые события;
- уведомления;
- блокировки;
- связи с другими процессами.

Этот документ не определяет:

- таблицы БД;
- API;
- frontend-компоненты;
- конкретный workflow engine;
- техническую реализацию очередей и уведомлений.

---

# 2. Общие правила workflows

## 2.1. Состояние — часть бизнес-логики

Статус сущности нельзя менять произвольно.

Каждый переход должен отвечать на вопросы:

1. кто имеет право выполнить переход;
2. из какого состояния;
3. в какое состояние;
4. какие условия должны быть выполнены;
5. какое событие создаётся;
6. кого необходимо уведомить;
7. можно ли отменить действие.

---

## 2.2. Прямое редактирование после согласования запрещено

Если сущность находится в состоянии:

- `APPROVED`;
- `ACCEPTED`;
- `CLOSED`;
- `ISSUED_FOR_WORK`;

изменение значимых данных выполняется только через:

- новую ревизию;
- корректировку;
- повторное открытие;
- аннулирование;
- отдельный override-процесс.

---

## 2.3. Workflow и задача — не одно и то же

Workflow описывает состояние бизнес-сущности.

Задача — действие, которое требуется от конкретного пользователя.

Пример:

`Документ = REVIEW_REQUIRED`

может создать задачу:

`ПТО: проверить новую ревизию`.

---

## 2.4. Событие создаётся после значимого перехода

Примеры:

- `DOCUMENT_REVISION_CREATED`;
- `WORK_PROGRESS_CONFIRMED`;
- `SUPPLY_REQUEST_APPROVED`;
- `QUALITY_ISSUE_CREATED`;
- `SAFETY_ADMISSION_BLOCKED`;
- `KS_APPROVED`.

Событие используется для:

- уведомлений;
- задач;
- Audit;
- аналитики;
- будущих интеграций.

---

## 2.5. Причина обязательна для негативных и административных переходов

Причина должна быть обязательной минимум для:

- возврата;
- отклонения;
- отмены;
- аннулирования;
- повторного открытия;
- override;
- изменения уже подтверждённых данных.

---

## 2.6. Организационный контекст перехода

Каждый переход выполняется не только от имени User/Role, но и в контексте ProjectOrganization. Действие, затрагивающее данные другой организации, требует explicit permission/scope или предусмотренного межорганизационного workflow. Совпадение Role внутри одного Project само по себе не даёт cross-organization доступа.

---

# 3. Общие классы состояний

Система может использовать общие смысловые группы, но конкретные статусы процесса должны быть отдельными.

## DRAFT

Данные создаются и могут свободно редактироваться автором/владельцем.

## REVIEW

Процесс передан другому участнику для проверки или решения.

## APPROVED / ACCEPTED

Сущность подтверждена ответственным лицом.

## IN_PROGRESS

Процесс исполняется.

## RETURNED

Возвращён на исправление.

## REJECTED

Отказано без автоматического продолжения.

## CANCELLED / ANNULLED

Процесс прекращён.

## CLOSED

Работа по процессу полностью завершена.

# 4. WF-01. Создание и запуск строительного объекта

## Назначение

Создание рабочего пространства объекта и подготовка его к эксплуатации.

## Владелец

Директор.

## Участники

- директор;
- директор по строительству;
- делопроизводитель;
- будущие участники проекта.

## Состояния

`DRAFT`  
→ `CONFIGURATION`  
→ `ACTIVE`  
→ `ARCHIVED`

Дополнительно:

`CANCELLED`

## Переходы

### DRAFT → CONFIGURATION

**Кто:** директор.

**Условия:**

- заполнены основные реквизиты объекта;
- определена организация;
- определены ключевые ответственные.

**Событие:** `PROJECT_CONFIGURATION_STARTED`.

---

### CONFIGURATION → ACTIVE

**Кто:** директор.

**Условия:**

- назначен директор по строительству;
- создана базовая структура объекта;
- назначены ключевые участники;
- определены зоны/захватки, если они уже известны.

**Событие:** `PROJECT_ACTIVATED`.

**Уведомления:**

всем назначенным участникам.

---

### ACTIVE → ARCHIVED

**Кто:** директор.

**Условия:**

- объект больше не должен принимать новые рабочие операции;
- причина архивирования указана.

**Эффект:**

- новые операционные процессы запрещены;
- история остаётся доступной.

**Событие:** `PROJECT_ARCHIVED`.

---

# 5. WF-02. Рабочая и проектная документация

## Назначение

Контроль актуальности документации, по которой выполняются работы.

## Владелец

ПТО.

## Согласующий производственного использования

Директор по строительству, если это подтверждается внутренним процессом организации.

## Состояния документа

`DRAFT`  
→ `REGISTERED`  
→ `UNDER_REVIEW`  
→ `APPROVED`  
→ `ISSUED_FOR_WORK`

Дополнительные:

`RETURNED`  
`SUPERSEDED`  
`ANNULLED`

## Переходы

### DRAFT → REGISTERED

**Кто:** ПТО / делопроизводитель в административной части.

**Условия:**

- документ идентифицирован;
- указан раздел/комплект;
- добавлен файл;
- определена ревизия.

**Событие:** `DOCUMENT_REGISTERED`.

---

### REGISTERED → UNDER_REVIEW

**Кто:** ПТО.

**Условия:**

- комплектность достаточна для проверки.

**Событие:** `DOCUMENT_SUBMITTED_FOR_REVIEW`.

---

### UNDER_REVIEW → RETURNED

**Кто:** проверяющий.

**Условия:**

- указана причина возврата.

**Событие:** `DOCUMENT_RETURNED`.

**Уведомление:** ПТО.

---

### UNDER_REVIEW → APPROVED

**Кто:** уполномоченный проверяющий.

**Условия:**

- документ проверен;
- отсутствуют блокирующие замечания.

**Событие:** `DOCUMENT_APPROVED`.

---

### APPROVED → ISSUED_FOR_WORK

**Кто:** директор по строительству / утверждённая роль.

**Условия:**

- документ разрешён для использования в производстве;
- определена область применения;
- если заменяется предыдущая версия — старая версия переводится в `SUPERSEDED`.

**События:**

- `DOCUMENT_ISSUED_FOR_WORK`;
- `DOCUMENT_SUPERSEDED`, если применимо.

**Уведомления:**

- начальник участка;
- мастера затронутых зон;
- ПТО;
- другие связанные роли.

---

### ISSUED_FOR_WORK → SUPERSEDED

Автоматически при вводе новой действующей ревизии.

Прямое редактирование старой ревизии запрещено.

---

### Любой активный статус → ANNULLED

**Кто:** ПТО + согласующий.

**Условия:**

- указана причина;
- определено влияние на связанные работы.

**Событие:** `DOCUMENT_ANNULLED`.

---

# 6. WF-03. Изменение рабочей документации

## Назначение

Обработка новой ревизии документа и её влияния на уже запланированные/выполняемые работы.

## Владелец

ПТО.

## Производственный владелец

Директор по строительству.

## Состояния изменения

`DETECTED`  
→ `IMPACT_ANALYSIS`  
→ `ACTION_REQUIRED` / `NO_IMPACT`  
→ `ACKNOWLEDGEMENT_REQUIRED`  
→ `RESOLVED`

Дополнительные:

`ESCALATED`

## Переходы

### DETECTED → IMPACT_ANALYSIS

Создана новая ревизия.

**Кто:** система + ПТО.

**Действия:**

- определить связанные захватки;
- определить связанные работы;
- определить ответственных.

---

### IMPACT_ANALYSIS → NO_IMPACT

**Кто:** ПТО + производственный ответственный.

**Условия:**

- изменение не влияет на текущие/будущие работы.

**Событие:** `DOCUMENT_CHANGE_NO_IMPACT`.

---

### IMPACT_ANALYSIS → ACTION_REQUIRED

**Условия:**

изменение влияет хотя бы на одну работу.

**Событие:** `DOCUMENT_CHANGE_IMPACT_FOUND`.

**Создаваемые задачи:**

- проверить работу;
- скорректировать план;
- остановить работу;
- обновить ИД;
- заказать дополнительные материалы — если применимо.

---

### ACTION_REQUIRED → ACKNOWLEDGEMENT_REQUIRED

Когда корректирующие действия определены.

**Уведомления:**

всем затронутым ответственным.

---

### ACKNOWLEDGEMENT_REQUIRED → RESOLVED

**Условия:**

- обязательные пользователи ознакомились;
- корректирующие задачи закрыты либо признаны не требующими исполнения.

**Событие:** `DOCUMENT_CHANGE_RESOLVED`.

---

### Любое активное состояние → ESCALATED

Если изменение создаёт критический риск для:

- безопасности;
- качества;
- сроков;
- стоимости;
- уже выполненных работ.

Уведомляются:

- директор;
- директор по строительству;
- владелец затронутого процесса.

---

# 7. WF-04. Ежедневное выполнение работ

## Назначение

Фиксация фактического производства на площадке.

## Владелец

Начальник участка.

## Основной исполнитель

Мастер.

## Состояния отчёта

`DRAFT`  
→ `SUBMITTED`  
→ `CONFIRMED`

Дополнительные:

`RETURNED`  
`CORRECTION_REQUIRED`  
`CORRECTED`

## Переходы

### DRAFT → SUBMITTED

**Кто:** мастер.

**Условия:**

- указана дата;
- выбраны работы;
- указан фактический объём;
- указана бригада/численность;
- зафиксированы существенные проблемы.

**Событие:** `DAILY_REPORT_SUBMITTED`.

---

### SUBMITTED → RETURNED

**Кто:** начальник участка.

**Условия:** указана причина.

---

### SUBMITTED → CONFIRMED

**Кто:** начальник участка.

**Эффект:**

фактические объёмы становятся подтверждёнными производственными данными.

**Событие:** `WORK_PROGRESS_CONFIRMED`.

---

### CONFIRMED → CORRECTION_REQUIRED

Прямое редактирование запрещено.

**Кто инициирует:** мастер / начальник участка.

**Условия:** причина корректировки.

---

### CORRECTION_REQUIRED → CORRECTED

После подтверждения корректировки ответственным.

Audit сохраняет исходные и новые значения.

---

# 8. WF-05. Планирование и производственная работа

## Назначение

Управление жизненным циклом конкретной строительной работы.

## Владелец

Директор по строительству.

## Оперативный владелец

Начальник участка.

## Состояния работы

`PLANNED`  
→ `READY`  
→ `IN_PROGRESS`  
→ `READY_FOR_INSPECTION`  
→ `ACCEPTED`  
→ `CLOSED`

Дополнительные:

`BLOCKED`  
`PAUSED`  
`REWORK_REQUIRED`  
`CANCELLED`

## Основные переходы

### PLANNED → READY

Условия:

- есть актуальная рабочая документация;
- определена зона;
- назначен ответственный;
- отсутствуют обязательные блокировки.

---

### READY → IN_PROGRESS

**Кто:** начальник участка.

Условия:

- выполнены требования допуска;
- необходимые документы доступны;
- работа разрешена к выполнению.

---

### IN_PROGRESS → BLOCKED

Причины:

- нет материала;
- изменение документации;
- нарушение ОТ/ТБ;
- замечание качества;
- техническая проблема;
- зависимая работа не завершена.

---

### BLOCKED → IN_PROGRESS

Только после устранения блокирующей причины.

---

### IN_PROGRESS → READY_FOR_INSPECTION

**Кто:** мастер/начальник участка.

Условия:

- этап физически завершён;
- обязательная первичная информация заполнена.

---

### READY_FOR_INSPECTION → ACCEPTED

Через workflow контроля качества.

---

### READY_FOR_INSPECTION → REWORK_REQUIRED

При замечании строительного контроля.

---

### ACCEPTED → CLOSED

Условия:

- качество принято;
- обязательные данные ИД присутствуют либо процесс допускает их последующее завершение;
- нет блокирующих замечаний.

Для текущего Work lifecycle реализованы только явно перечисленные переходы:
`PLANNED → READY`, `READY → IN_PROGRESS`, `IN_PROGRESS → BLOCKED`,
`BLOCKED → IN_PROGRESS`, `IN_PROGRESS → READY_FOR_INSPECTION`,
`READY_FOR_INSPECTION → ACCEPTED`,
`READY_FOR_INSPECTION → REWORK_REQUIRED`, `ACCEPTED → CLOSED`.
Статусы `PAUSED` и `CANCELLED` зарезервированы, но переходы в них не разрешены
до отдельного утверждения условий и владельцев процесса.
Обратный переход из `REWORK_REQUIRED` также не определён в WF-05 и не добавлен.
Каждая команда повторяется без новой истории, если Work уже в её целевом
состоянии; из любого другого недопустимого состояния команда завершается
ошибкой. Реальный переход атомарно создаёт AuditEntry и Event
`work.status_changed` с исходным и новым статусами. Изменение Work не закрывает
Task или DocumentImpact и не подтверждает Notification.

# 9. WF-06. Заявка на материалы

## Назначение

Преобразовать производственную потребность в контролируемую заявку снабжению.

## Владелец

Снабженец.

## Инициаторы

- мастер;
- начальник участка.

## Состояния

`DRAFT`  
→ `SUBMITTED`  
→ `PRODUCTION_CONFIRMED`  
→ `APPROVED`  
→ `IN_SUPPLY`  
→ `ORDERED`  
→ `PARTIALLY_DELIVERED` / `DELIVERED`  
→ `CLOSED`

Дополнительные:

`RETURNED`  
`REJECTED`  
`CANCELLED`  
`DELAYED`

## Переходы

### DRAFT → SUBMITTED

**Кто:** инициатор.

Условия:

- материал;
- количество;
- единица;
- требуемый срок;
- связанная работа/зона;
- комментарий при необходимости.

---

### SUBMITTED → PRODUCTION_CONFIRMED

**Кто:** начальник участка.

Подтверждает, что заявка действительно необходима производству.

---

### PRODUCTION_CONFIRMED → APPROVED

**Кто:** директор по строительству / директор по лимитам.

Правило согласования зависит от стоимости/критичности и будет уточнено позже.

---

### APPROVED → IN_SUPPLY

**Кто:** снабженец.

Событие: `SUPPLY_REQUEST_ACCEPTED`.

---

### IN_SUPPLY → ORDERED

Поставка/заказ подтверждены.

---

### ORDERED → DELAYED

Если срок поставки нарушается.

Уведомления:

- начальник участка;
- заявитель;
- директор по строительству, если задержка влияет на график.

---

### ORDERED → PARTIALLY_DELIVERED

Поставлена часть количества.

---

### ORDERED/PARTIALLY_DELIVERED → DELIVERED

Поставлен необходимый объём.

---

### DELIVERED → CLOSED

После регистрации поставки и необходимых проверок.

---

# 10. WF-07. Поставка и входной контроль ТМЦ

## Назначение

Проверить, что поставленный материал может использоваться в строительстве.

## Владельцы

- снабжение — поставка;
- строительный контроль — качество входного контроля.

## Состояния партии

`RECEIVED`  
→ `DOCUMENT_CHECK`  
→ `QUALITY_CHECK`  
→ `ACCEPTED`

Дополнительные:

`QUARANTINE`  
`REJECTED`  
`PARTIALLY_ACCEPTED`

## Переходы

### RECEIVED → DOCUMENT_CHECK

Проверяются:

- количество;
- наименование;
- поставщик;
- договор/заявка;
- документы качества.

---

### DOCUMENT_CHECK → QUALITY_CHECK

Документы комплектны.

---

### DOCUMENT_CHECK → QUARANTINE

Если документов недостаточно.

Материал не должен считаться полностью допущенным к использованию.

---

### QUALITY_CHECK → ACCEPTED

**Кто:** инженер строительного контроля.

Условия:

- материал соответствует требованиям.

**Событие:** `MATERIAL_ACCEPTED`.

---

### QUALITY_CHECK → PARTIALLY_ACCEPTED

Часть партии принята, часть имеет проблему.

---

### QUALITY_CHECK → REJECTED

Материал не соответствует требованиям.

**Событие:** `MATERIAL_REJECTED`.

**Уведомления:**

- снабженец;
- начальник участка;
- директор по строительству.

---

# 11. WF-08. Строительный контроль выполненных работ

## Назначение

Контроль качества выполненной работы до перехода к следующему этапу.

## Владелец

Инженер строительного контроля от генподрядчика.

## Состояния проверки

`REQUESTED`  
→ `SCHEDULED`  
→ `IN_INSPECTION`  
→ `ACCEPTED`

Дополнительные:

`ISSUES_FOUND`  
`REWORK_IN_PROGRESS`  
`REINSPECTION_REQUIRED`  
`CANCELLED`

## Переходы

### REQUESTED → SCHEDULED

Инженер контроля принимает вызов.

---

### SCHEDULED → IN_INSPECTION

Начало проверки.

---

### IN_INSPECTION → ACCEPTED

Условия:

- требования качества выполнены;
- отсутствуют блокирующие замечания.

**Событие:** `WORK_QUALITY_ACCEPTED`.

---

### IN_INSPECTION → ISSUES_FOUND

Создаётся одно или несколько замечаний.

Каждое замечание должно иметь:

- описание;
- привязку к работе/зоне;
- критичность;
- ответственного;
- срок исправления;
- подтверждающий материал при необходимости.

---

### ISSUES_FOUND → REWORK_IN_PROGRESS

Начальник участка назначает устранение.

---

### REWORK_IN_PROGRESS → REINSPECTION_REQUIRED

Исполнитель сообщает об устранении.

---

### REINSPECTION_REQUIRED → ACCEPTED

Инженер контроля подтверждает устранение.

---

### REINSPECTION_REQUIRED → ISSUES_FOUND

Если замечание устранено не полностью.

---

# 25. Классы блокировок

Не каждая проблема должна одинаково блокировать работу.

## INFO

Не блокирует процесс.

Пример:

документ истекает через 30 дней.

## WARNING

Работа может продолжаться, но требуется реакция.

Пример:

поставка рискует опоздать.

## BLOCKING

Переход в следующее состояние запрещён.

Примеры:

- нет обязательного допуска;
- материал не прошёл входной контроль;
- работа имеет блокирующее замечание;
- рабочая документация аннулирована.

## CRITICAL

Требует немедленной эскалации и потенциальной остановки процесса.

Примеры:

- критическое нарушение ОТ;
- использование аннулированной документации;
- критическое замечание качества.

# 28. Запрещённые переходы

Система не должна позволять:

1. начать работу без требуемой действующей рабочей документации;
2. использовать аннулированную ревизию как текущую;
3. свободно изменить подтверждённый ежедневный объём;
4. закрыть замечание исполнителем без требуемой проверки;
5. считать материал допущенным, если он находится в `QUARANTINE` или `REJECTED`;
6. принять качество работы пользователю без соответствующего полномочия;
7. закрыть комплект ИД при отсутствии обязательных компонентов;
8. включить один и тот же объём в КС повторно;
9. редактировать закрытую КС без корректировки;
10. считать оплату выполненной без фиксации подтверждающего факта;
11. назначить сотрудника на специальную работу при блокирующем отсутствии допуска;
12. продолжать работу по приостановленному наряду-допуску;
13. удалять историю значимых бизнес-операций;
14. считать обязательную геодезическую контрольную точку пройденной без принятого GeodeticSurvey;
15. изменять подтверждённую JournalEntry in-place вместо корректирующей ревизии.

# 29. Что должно отображаться пользователю как «Моя работа»

На основе workflows система сможет формировать единый список:

## Требует моего действия

Например:

- согласовать заявку;
- подтвердить ежедневный отчёт;
- устранить замечание;
- проверить ИД;
- ознакомиться с новой ревизией;
- продлить удостоверение;
- принять поставку.

## Просрочено

Все задачи/этапы, срок которых прошёл.

## Заблокировано

Процессы, которые не могут продолжаться.

## Ожидаю другого участника

Например:

- ждём согласование;
- ждём поставку;
- ждём проверку;
- ждём устранение замечания.

# 30. Definition of Done для бизнес-workflow

Workflow считается достаточно определённым для проектирования domain model, если для него известны:

- владелец;
- основная сущность;
- состояния;
- переходы;
- права на переход;
- блокирующие условия;
- создаваемые события;
- связанные роли;
- связанные процессы;
- правила изменения после согласования.

# 31. Открытые вопросы

До реализации соответствующих процессов требуется уточнить:

1. Кто официально выдаёт документацию «в производство»?
2. Кто финально проверяет/принимает ИД?
3. Какие согласования заявок на ТМЦ зависят от суммы?
4. Нужен ли отдельный складской процесс и кладовщик?
5. Кто подписывает входной контроль кроме инженера строительного контроля?
6. Какие виды работ требуют обязательного наряда-допуска?
7. Какие ОТ/ТБ нарушения являются `WARNING`, а какие `BLOCKING/CRITICAL`?
8. Требуется ли электронная подпись для отдельных журналов/актов?
9. Кто финально согласует КС со стороны организации?
10. Кто фиксирует факт оплаты?
11. Нужны ли отдельные внешние workflows с заказчиком и субподрядчиком?
12. Как обрабатываются аварийные дополнительные работы, которые нельзя ждать полного согласования?
13. Нужен ли обязательный SLA на согласования/проверки?
14. Какие события требуют обязательного подтверждения ознакомления?
